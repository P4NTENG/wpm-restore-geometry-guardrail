# Chrome 창 크기 드리프트 — 조사 보고서

**작성일:** 2026-09-29 (개정 5 — 원인 확정 및 해결 검증)
**대상:** Google Chrome (Chromium/Electron 계열)

## 결론

**원인이 확정되었다.** §12~§14의 3단계 배치 대조 실험으로 검증했다.

배치 조건별 관측:

| 조건 | 가장 왼쪽 | 위치 조회 배율 | 복원 시 최소 폭 하한 | zone 폭 974 |
|---|---|---|---|---|
| 노트북 주+왼쪽 | 노트북 200% | 2.0 | ≈1016 | 클램프 |
| DEL 주, 노트북 왼쪽 | 노트북 200% | 2.0 | ≈1016 | 클램프 |
| **DEL 가장 왼쪽** | **DEL 100%** | **1.0** | **516** | **유지** |

**기전:** Chromium은 un-minimize 시 **주 모니터가 아니라 창의 위치로** 디스플레이를 결정한다. 최소화 위치 `(-32000,-32000)`는 유효하지 않아 **가장 왼쪽 디스플레이**로 해석되며(§13-3, §14-1에서 직접 측정), 그 배율을 최소 트랙 크기에 곱한다. 200%로 오인되면 최소 폭이 부풀어 **하한 1016**이 생겨, 그보다 좁은 zone(974)이 복원 시마다 늘어난다. 하한이므로 누적되지 않고 좌측만 고정한 채 우측으로 늘어나 1회 후 고정된다.

**해결:** 100% 모니터를 가장 왼쪽에 배치. §14에서 **WPM 없이도** Chrome·Slack 모두 3회 이상 크기가 고정됨을 확인했다.

> **개정 1의 정정:** 초판은 "값은 프로세스 메모리에만 존재한다"고 단정했으나 이는 §4의 추측에 해당하며 §6.3/§10이 미해결로 적고 있었다. 또한 "프로필 파일은 전부 실패"는 §2-4에서 `Default\Preferences`가 실제 저장소로 확인된 사실과 충돌했다.
>
> **개정 4→5:** §13에서 "주 모니터 지정"이 해결책이라고 했으나 실험에서 **기각**됐다. 임계값이 1016 그대로였다. 조건은 "주 모니터"가 아니라 **"가장 왼쪽"** 이며, §14에서 이를 검증했다. **§2의 저장소 조사(§2-4~2-10)는 모두 실패했지만, 그것은 이 문제가 저장소 문제가 아니라 배율 산출 문제였기 때문이다.** 하한이 `WINDOWPLACEMENT`·프로필·레지스트리를 무시하고 OS가 직접 적용하므로, 올바른 대상을 쓰고 있었다면 해결될 수 없었다.

**남는 미해결 3건:**
1. 하한 `1016`이 실측 최소 폭 `516`의 정확히 2배가 아닌 이유 (**1.969배**). 투명 테두리 관련로 추정하나 미확정. §14에서 하한이 516이 되어 관측 범위에서 사라졌다.
2. Chrome 재시작 후 나타나는 `1554x1290`. 높이까지 변하므로 최소 폭 클램프로는 설명되지 않으며, **현 배치에서 재현 여부를 확인하지 않았다.**
3. Chromium 소스 미검토. 위 기전은 전부 Black-box 관측에 근거한다.

## 1. 문제 요약

Chrome 창을 FancyZones zone에 넣으면 크기는 정확히 맞는다. 그런데 최소화 후 복원하면 **폭이 +42px**로 늘어나고 복원할 때마다 다시 늘어난다.

```
zone 배치 직후   : 3833,228 974x1039   (정상)
최소화          : -32000,-32000 314x50
복원            : 3833,228 1016x1039   ← 폭 +42px
복원(2회차)     : 3833,228 1016x1039   ← 더 늘어나지 않음
```

**드리프트는 누적 오차가 아니다.** 974 → 1016으로 **한 번 변한 뒤 고정**된다. 즉 매 복원마다 증가하는 것이 아니라, **캐시된 값 1016을 반복해서 재적용하는 패턴**이다. (초판에 "복원할 때마다 늘어난다"고 적었으나 데이터와 불일치 — 아래 §11-1 참조.)

### zone 기하 (실측)

| 항목 | 값 |
|---|---|
| 모니터 | 96 DPI 외장 모니터, 작업영역 `2880,228 1920x1032` |
| 레이아웃 | columns, 2 zones |
| zone 0 (왼쪽) | `2874,228 972x1038` (Slack 확인) |
| zone 1 (오른쪽) | `3833,228 974x1039` (Chrome 확인) |
| invisible border | 좌 −7, 상 0, 우 +7, 하 +7 |
| zone 1 실제 보이는 폭 | `3840..4800` = 960px |

### 넘치는 크기

| 측정 | 부팅 후 정상 | 복원 후 드리프트 | 차이 |
|---|---|---|---|
| 창 rect (GetWindowRect) | 974 | 1016 | **+42** |
| 보이는 프레임 (DWM) | 960 | 1002 | **+42** |
| 오른쪽 끝 (작업영역 4800 기준) | 4800 | 4842 | **+42 초과** |

좌측 끝은 `3833`으로 고정이고 **오른쪽으로만** 밀린다. `WINDOWPLACEMENT`가 아니라 앱 내부의 좌우 비대칭 처리와 관련되었을 가능성이 있으나, 이는 **추측이며 확인하지 못했다.**

## 2. 검증한 사실 (실험과 수치)

아래는 모두 실제 실행·측정한 결과다. 추정은 별도로 표시했다.

### 2-1. `WINDOWPLACEMENT`는 정확하지만 Chrome이 무시한다

zone 크기 `974x1039`로 있을 때 minimize→restore 관측:

```
start      rcNormal=3833,228 974x1039   actual=3833,228 974x1039
minimized  rcNormal=3833,228 974x1039   actual=-32000,-32000 314x50
restored   rcNormal=3833,228 974x1039   actual=3833,228 1016x1039
```

`rcNormalPosition`(= 셸이 복원에 쓸 사각형)은 **시작부터 끝까지 974로 정확**한데, 실제 창은 1016이 된다. 셸의 값은 정상이므로 문제는 셸 쪽이 아니다.

### 2-2. `SetWindowPos`로 974로 맞춰도 복원하면 되돌아간다

```
start      rcNormal=3833,228 974x1039    actual=3833,228 974x1039
minimized  rcNormal=3833,228 974x1039    actual=-32000,-32000 314x50
restored   rcNormal=3833,228 974x1039    actual=3833,228 1554x1290
```

**974x1039가 `WINDOWPLACEMENT`에 정확히 들어있는데도** 복원하니 1554x1290로 복귀한다. → `WINDOWPLACEMENT`는 원인이 아니다.

### 2-3. 복원 후 `rcNormal` 자체가 1554x1290로 바뀐다

2-2에서 복원 직후 `rcNormal`이 1554x1290가 되었다. 즉 창을 리사이즈한 주체가 Chrome이고, Chrome이 자신의 크기를 `WINDOWPLACEMENT`에 다시 써 넣는다.

### 2-4. `Default\Preferences`의 `browser.window_placement`에 1016x1039가 실제로 들어있었다

```
%LOCALAPPDATA%\Google\Chrome\User Data\Default\Preferences
```

```json
"window_placement": {
  "bottom": 1153, "left": 2393, "maximized": false,
  "right": 3409, "top": 114,
  "work_area_bottom": 1146, "work_area_left": 1440,
  "work_area_right": 3360, "work_area_top": 114
}
```

- 폭 = 3409 − 2393 = **1016**
- 높이 = 1153 − 114 = **1039**

드리프트 값과 **정확히 일치**한다. 즉 이것은 Chrome이 실제로 창 경계를 보관하는 진짜 저장소로 **확인됐다.**

같은 파일에 있는 관련 키:
- `browser.app_window_placement` — 1060x832, maximized
- `browser.window_placement_popup` — 616x935
- `account_values...exceptions.window_placement` — `{}` (콘텐츠 설정 예외, 무관)
- `profile...exceptions.window_placement` — `{}` (무관)

### 2-5. 그 값을 974x1039로 써도 복원 결과는 안 바뀐다 — 단, 좌표 공간이 틀렸던 실험

Chrome을 **완전히 종료**한 상태에서 위 값을 `3833,228 974x1039`(물리 좌표)로 덮어쓴 뒤 재실행:

```
start      rcNormal=2869,228 982x1043     actual=2869,228 982x1043
minimized  rcNormal=2869,228 982x1043     actual=-32000,-32000 314x50
restored   rcNormal=2869,228 982x1043     actual=2869,228 1554x1290
```

**초판의 오류 — 좌표 공간 불일치.** 이 실험은 **잘못된 좌표계에서 실행됐다.**

Preferences에 기록된 작업영역은 `(1440,114)-(3360,1146)`이고 실측 물리 작업영역은 `(2880,228)-(4800,1260)`이다. **원점이 정확히 절반이고 크기(1920x1032)는 동일**하다. 또한 기록된 `left` 2393은 `3833 − 1440`과 일치한다.

즉 **Chrome은 노트북을 0~1440으로 두는 DIP(논리) 좌표계에 저장**하며, DEL 영역의 변환은 `logical = physical − 1440`, `logical_y = physical_y − 114`다. 물리값 `3833,228`을 그대로 쓰면 Chrome 입장에서는 약 `5273,342`가 되어 자기 작업영역(1440~3360) 밖이 되고, 따라서 임의 보정되어 `2869 / 982x1043`으로 보정되었다.

**재시험 시 사용할 값:** `left=2393, top=114, right=3367, bottom=1153`

**따라서 이 실험의 결론은:**
- "복원 경로와 무관하다"는 **여전히 유력하나 이 실험으로는 검증되지 않았다.** (복원이 파일을 읽지 않는다는 논리는 유효하나, 실험이 좌표 오류로 오염됐다.)
- "생성 위치에는 영향을 줄 수 있다"도 **미검증**이다. `982x1043`은 잘못된 입력에 대한 Chrome의 보정 결과일 뿐이다.
- **미실험 상태로 남긴다.**

### 2-6. 실행 옵션 `--window-size`도 무시된다 — 역시 좌표 공간 문제

```
chrome.exe --window-size=974,1039 --window-position=3833,228
```

- 열린 결과: `2869,228 982x1043` (요청 크기를 따르지 않음)
- minimize→restore: `1554x1290`

§2-5와 동일한 DIP/물리 불일치의 영향으로 보인다. **--window-size는 DIP를 받으므로** 물리값을 넣으면 어긋난다. 이 실험 역시 좌표 공간이 맞지 않아 **재시험이 필요하다.**

### 2-7. 네이티브 스냅(Win+Left)은 크기를 맞춰주지만 복원 시 덮어써진다

```
before Win+Left : 3833,228 1554x1290
after  Win+Left : 2873,228 974x1039      ← 크기 정상 적용됨
cycle 1 최소/복원: 2873,228 1554x1290   ← 위치는 유지, 크기만 되돌아감
```

**위치는 `2873`으로 유지되는데 크기만 1554x1290로 복귀**한다. 위치와 크기가 별개 경로로 처리된다는 점은 후에 관찰한 "+42px 우측 전이"와 정합한다.

### 2-8. 세션 파일에는 1554x1290가 없다

`Default\Sessions\*.bin`을 int32 LE 패턴으로 스캔:

| 파일 | 974x1039 근처쌍 | 1016x1039 근처쌍 | 1554x1290 |
|---|---|---|---|
| `Session_13435113797299791` | 9 | 0 | **0** |
| `Session_13435118415131814` | 13 | 22 | **0** |
| `Session_13435119955860751` | 60 | 33 | **0** |
| `Tabs_13435112767472109` | 0 | 0 | **0** |
| `Tabs_13435114823109879` | 1 | 0 | **0** |

974x1039와 1016x1039 쌍은 다수 존재하지만 **1554x1290는 어디에도 없다.** 즉 Chrome이 복원 시 실제로 쓰는 그 값은 세션 파일에도 없다.

### 2-9. Preferences 안의 `1554` 검색 — 방법 오류였고, 정정 후 재실행

**초판의 오류.** Preferences는 폭이 아니라 `left/right/top/bottom`을 저장한다(§2-4에서 직접 확인). 따라서 폭 `1554`는 문자열로 나타나지 않고 `right − left`로만 존재한다. 문자열 `"1554"` 검색은 **방법이 틀렸고**, "5건 전부 우연"이라는 관찰은 "다른 저장소 없음"의 근거가 되지 못한다.

**정정 후 재실행.** `left/right/top/bottom`을 가진 모든 JSON 객체를 찾아 차이를 계산했다.

| 파일 | 키 | 크기 | 원본 |
|---|---|---|---|
| Local State | `task_manager.window_placement` | 974x1032 | L2386 T114 R3360 B1146 |
| Preferences | `browser.app_window_placement._crx_...` | 1050x832 | L10 T10 R1060 B842 |
| Preferences | `browser.window_placement` | 971x1035 | L2393 T114 R3364 B1149 |
| Preferences | `browser.window_placement_popup` | 616x935 | L1440 T125 R2056 B1060 |

**`1554x1290`은 어디에도 존재하지 않는다.** 결론은 같으나 이번에는 방법이 맞다. (위 표는 측정 시점 값이며 이후 zone 배치에 따라 `browser.window_placement`이 갱신됨.)

### 2-10. Ctrl(Shift) 누르고 X로 닫아 강제 저장 — 동작하지 않음

사용자가 직접 시험. 결과: 크기 유지 실패.

## 3. 조사한 저장소 후보와 결과 요약

| # | 위치 | 접근법 | 결과 |
|---|---|---|---|
| 1 | `WINDOWPLACEMENT.rcNormalPosition` | SetWindowPlacement 직접 기록 | **실패** (2-2). 값은 정확하나 Chrome이 무시 |
| 2 | `Local State` → `browser.window_placement` | 값 변조 | **실패.** 초판은 "파일이 잘못됨"이라고 적었으나 **근거 미제시였다.** 정정: `browser.window_placement`의 진짜 위치는 §2-4의 `Default\Preferences`이며, Local State에는 `task_manager.window_placement`만 존재한다(§2-9). Local State 변조 실험은 §2-9 표에 남은 값 기준으로 재평가 필요 |
| 3 | `Default\Preferences` → `browser.window_placement` | 값 변조 (Chrome 종료 상태) | **무효.** §2-5 — DIP/물리 좌표 불일치로 실험이 오염됨. 재시험 필요 |
| 4 | `chrome.exe --window-size/--window-position` | 실행 옵션 | **무효.** §2-6 — 좌표 공간 불일치. 재시험 필요 |
| 5 | 네이티브 Aero Snap (Win+Left) | 키 입력 | **부분 성공 후 실패** (2-7). 크기 적용은 되나 복원에서 덮어씀. **단, `fancyzones_overrideSnapHotkeys`가 꺼져 있어야 순수한 네이티브 대조군이다 — 현재 true로 확인되어 이 실험은 FancyZones 영향이 섞여 있을 수 있다** |
| 6 | `Default\Sessions\*.bin` | 이진 패턴 스캔 | **해당 값 부재** (2-8) |
| 7 | 레지스트리 `BagMru` | 조회 | **무관.** Chrome/Slack 미추적 |
| 8 | 레지스트리 `ShellBags` | 조회 | **무관.** Explorer 폴더별 상태 전용 |
| 9 | `Control Panel\Desktop\WindowMetrics` | 조회 | **무관.** 전역 프레임 기본값. 이 버그와 관계없음 |
| 10 | Ctrl/Shift + X 강제 저장 | 사용자 시험 | **실패** (2-10) |

### 일반적 가이드에 대한 평가

범용 문서(레지스트리 → AppData 파일 → 설치 폴더 3단계)는 **이 문제에 해당하지 않는다.**

- 레지스트리 저장은 Win32 네이티브 앱(예: Notepad의 `iWindowPosX`)의 방식이다.
- Chromium/Electron 앱은 기본적으로 자기 geometry를 OS에 맡기며, 그래서 애초에 이 문제가 발생한다.
- Chrome의 실제 창 경계는 AppData JSON(`Default\Preferences`)에 있었다. 즉 3단계 중 **2단계**에 해당한다.
- **주의:** `WindowMetrics` 키 삭제는 재부팅이 필요한 파괴적 변경이며 이 버그와 무관하다. 삭제하지 말 것.

## 4. 메커니즘 (개정 3 기준 일부 확인)

초판에는 전부 추측으로 적었으나, §12에서 **폭 하한 클램프** 부분이 실험으로 확인되었다. 확인된 것과 아직 추측인 것을 구분한다.

### 확인된 부분 (§12)

복원 시 Chromium이 **최소 트랙 크기**를 적용하는데, 이때 디스플레이 배율을 **최소화된 창의 위치에서** 구한다. 최소화된 위치 `(-32000,-32000)`는 어떤 디스플레이에도 속하지 않으므로 **그 점에 가장 가까운, 즉 가장 왼쪽 디스플레이**로 해석된다(§13-3에서 직접 측정). Chromium은 **주 모니터를 조회하지 않는다**(§13-2에서 주 모니터 변경으로 임계값이 그대로임을 확인).

배율은 **최소 트랙 크기 전체가 아니라 콘텐츠 최소 폭에만** 곱해진다. 하한은 아래 식으로 두 실측값과 정확히 일치한다.

```
하한 = 500 × 배율 + 16
      500 = Chrome 최소 콘텐츠 폭
       16 = 프레임(투명 테두리 14 + 보이는 테두리 2), 배율 영향 없음

배율 1.0 (100% 모니터가 왼쪽) →  500 + 16 =  516   ← §14-2 실측 일치
배율 2.0 (200% 모니터가 왼쪽) → 1000 + 16 = 1016   ← §12-3 실측 일치
```

그 결과 복원 시점에 하한이 적용되어, 그보다 좁은 창(zone 폭 974)만 키워진다.

근거: 폭 스윕에서 1016에서 뚜렷한 계단 함수(§12-3), DEL을 가장 왼쪽으로 바꾸자 하한이 516으로 내려가 계단 함수가 사라짐(§14-2). 배율이 창 크기 전체에 곱해졌다면 비례 오차가 났을 것이고, 최소 크기 하한이므로 계단 함수가 되는 기하와 일치한다.

**이 식에서 얻는 예측:** 왼쪽 모니터를 150%로 바꾸면 하한은 `500 × 1.5 + 16 = 766`이 된다. 미검증.

### 아직 추측인 부분

1. Chromium이 배율을 **어떤 API로** 구하는지는 소스를 검토하지 않았다. 위치 기반 조회가 실제로 쓰인다는 것은 §13-2/§14-2/§16-1(§16 실험 결과 문서)에서 확인되었다. **단, `GetDpiForWindow`는 그 경로가 아니다** — §16에서 `ptMinTrackSize.x`가 1016인 **모든 9개 샘플에서 `GetDpiForWindow`는 96**이었고, 전체 395,966개 샘플 전 구간 96이었다. 두 값이 같은 순간에 서로 다른 값을 보이는 것이므로 `minTrack = f(GetDpiForWindow)`는 성립하지 않는다.
2. Electron이 최소 크기에 디스플레이 배율을 곱한다는 것은 **외부 소스 기반 진술**이며, 이 환경에서 직접 검증하지 않았다.
3. Slack이 새지 않는 이유. Electron 쪽에 대응 수정이 있을 수 있다는 것은 가설이다.

### 설명되지 않는 부분

왜 값이 세션 중에는 1016이고, Chrome 재시작 후에는 `1554x1290`(높이까지 변함)이 되는지는 **설명하지 못했다.** `1554x1290`는 §2-9에서 프로필·세션 파일에 없음을 재확인했다. 최소 폭 클램프만으로는 높이가 변할 수 없어 **별개 현상으로 보이나, §12-A2에서는 재현되지 않아 미확인이다.**

## 5. 실제로 동작하는 해결책

외부 저장은 불가능하므로, **복원이 일어난 직후 크기를 교정**하는 방식으로 해결했다. (Window Position Manager / WPM)

### 동작 원리

1. **배움 (관찰 기반)** — 레이아웃을 계산하지 않는다. 창이 실제로 **이동**하고 1.2초간 안정되면 그 사각형을 zone rect로 기록한다. 크기만 바뀐 경우는 배우지 않는다(그게 바로 드리프트라서).
2. **매칭 (앱별 목록 + 최근접)** — 앱별로 zone rect 목록을 갖고, 각 창을 **위치가 가장 가까운** 항목에 매칭한다. Chrome 창이 여러 개여도 각자 제 zone에 매칭된다.
3. **교정** — 최소화→복원 전환이 발생하고 ①크기가 다르고 ②위치가 여전히 그 zone 자리일 때만 배운 사각형을 재적용한다.
4. **지속** — `WindowZones.ini`에 저장되어 로그인/재시작에도 유지된다.

### 안전장치

| 장치 | 이유 |
|---|---|
| 크기만 바뀌면 배우지 않음 | 드리프트를 zone으로 배워버리는 것을 방지 |
| 교정 전 위치 확인 | 사람이 옮긴 창을 되돌려 논쟁하지 않음 |
| 크기가 맞으면 아무것도 안 함 | 불필요한 SetWindowPos 없음 |
| 같은 자리 항목은 교체 | 레이아웃 변경 시 목록 무한 증가 방지 |
| 앱당 최대 6개 | 낡은 레이아웃이 뒤로 밀림 |

### 검증 결과

zone 파일 내용:
```
[Zones]
chrome.exe|Chrome_WidgetWin_1=3833,228,974,1039
```

의도적으로 크기를 `1300`으로 왜곡한 뒤 최소→복원:
```
baseline : 3833,228 1300x1039   ← 시험상 만든 상태
cycle 1  : 3833,228 974x1039   ← WPM이 교정
cycle 2  : 3833,228 974x1039
cycle 3  : 3833,228 974x1039
```

교정 후 zone 파일은 `974,1039` **그대로** — 위치가 안 변했으므로 변조된 크기를 배워버리지 않았다. 의도한 대로 동작했다.

Slack은 `972x1038`로 자체 안정 확인(3회).

## 6. 남는 제약

**1. 배움에는 "관측"이 필요하다.**
창이 실제로 이동해야 배워진다. 이미 제자리에 멈춰 있는 앱은 배우지 못한다. Slack이 zone 파일에 없는 이유가 이것이다(지금은 자체적으로 안 새서 무방).

**2. 타이밍 경쟁이 간헐적으로 생긴다.**
Chrome이 WPM의 교정 *이후에* 자기 크기를 다시 씌우는 경우가 관측되었다(1회). 다음 복원에서 바로잡혔으나, 드리프트가 한 사이클 동안 보이는 일은 있을 수 있다.

**3. 1554x1290의 출처는 미해결.**
재시작 후 나타나는 이 값의 저장소를 찾지 못했다.

**4. Slack 등 다른 앱은 미검증.**
Chrome 기준으로만 검증했다.

## 11. 혼합 DPI 검증 (개정 2에서 추가)

### 11-1. 드리프트 패턴의 정정

초판은 "복원할 때마다 늘어난다"고 기술했으나 실측은 다음과 같다.

```
cycle 1 : 3833,228 1016x1039
cycle 2 : 3833,228 1016x1039
cycle 3 : 3833,228 1016x1039
```

**한 번 변한 뒤 고정**된다. 누적 오차가 아니라 **캐시된 값의 재적용**이다. 이 구분이 중요하다 — 누적 오차라면 매번 더 커져야 하고, 재적용이라면 값이 하나로 수렴해야 하기 때문이다. WPM이 개입하지 않았을 때의 원시 데이터다.

### 11-2. DIP 좌표계 확인 (설계상 착각의 근거)

직접 Preferences를 읽어 확인한 결과(§2-9 표):

```
Preferences  browser.window_placement  L2393 T114 R3364 B1149
실측 물리                                          3834,230  971x1035
```

- `2393 + 1440 = 3833`
- `114 + 114 = 228`
- 크기 `971x1035` 일치

**Chrome은 노트북을 0~1440(논리폭)로 두는 DIP 좌표계에 저장하며, DEL 영역은 `logical = physical − 1440`이다.** Preferences의 `work_area_left` 1440도 이 프레임과 일치한다.

이 사실은 §2-5/2-6의 실험이 왜 실패했는지(입력이 자기 작업영역 밖이라 보정되었는지)를 설명한다.

### 11-3. 최소화된 창에 대한 두 API의 상반된 응답

`MonitorFromWindow(hwnd, MONITOR_DEFAULTTONEAREST)`와 `GetDpiForWindow`, 그리고 창 rect를 동시 관측:

| 상태 | 창 rect | GetDpiForWindow | MonitorFromWindow(NEAREST) | 해당 모니터 DPI |
|---|---|---|---|---|
| 일반 | 4345,304 | 96 DPI (=100%) | `0x20001` (DEL) | 96 DPI (=100%) |
| **최소화** | **0,1654** | 96 DPI (=100%) | `0x20001` (DEL) | 96 DPI (=100%) |
| 복원 | 4345,304 | 96 DPI (=100%) | `0x20001` (DEL) | 96 DPI (=100%) |

**관측된 사실:**
- 최소화 중에도 `MonitorFromWindow`는 **올바른 모니터(DEL)** 를 반환한다.
- 그러나 **창 rect는 `0,1654`로 x=0**, 즉 노트북(200%) 영역에 놓인다. 다른 창에서는 `-32000,-32000`으로 최소화되었다 — **최소화 rect는 창마다 다르다**(본 조사에서 두 종류를 확인).

**이 문장은 §13-3에서 직접 측정되었다.** `MonitorFromPoint(-32000,-32000)`는 이 배치에서 노트북(200%)을 반환했고, DEL을 가장 왼쪽으로 옮기면 DEL(100%)을 반환했다(§14-1). §16에서 `WM_GETMINMAXINFO.ptMinTrackSize.x` 자체가 이 조건에 따라 1016/516으로 변함을 직접 관측했다.

HWND 기반 API(`MonitorFromWindow`)는 정상이라는 관찰과, 문제가 위치 기반 조회라는 설명은 **모순되지 않는다.**

### 11-4. 대조 실험: 동일 창을 두 모니터에 배치

> **"결정적"은 과장이다.** 표본이 **창 1개**이고, FancyZones 배치 상태에서의 측정이었으며, 주/보조 모니터 구분이라는 변수가 남아 있다. 아래 결론은 이후 §12-A2에서 교란 없이 재확인되었다.

WPM을 정지시키고, **같은 Chrome 창**을 두 모니터에 각각 두어 최소→복원을 3회 반복했다.

```
A) DEL (96 DPI, 1920x1032)
   base : 3833,228 974x1039
   cyc1 : 3833,228 1016x1039   ← +42px 드리프트
   cyc2 : 3833,228 1016x1039
   cyc3 : 3833,228 1016x1039

B) 노트북 (192 DPI, 2880x1704)
   base : 200,200 2800x1600
   cyc1 : 200,200 2800x1600    ← 드리프트 없음
   cyc2 : 200,200 2800x1600
   cyc3 : 200,200 2800x1600
```

**200% 주 모니터에서는 드리프트가 하나도 없다. 100% 보조 모니터에서만 발생한다.**

부수 관찰: B에서 물리 `1400x800`을 요청했으나 실제로는 `2800x1600`이 되었다. **이는 다른 DPI 모니터로 `SetWindowPos`를 할 때 Windows가 크기를 DPI 비율로 스케일하는 표준 동작**으로 더 단순하게 설명된다. **Chrome의 DIP/물리 혼용 증거로 볼 수 없다.** (초판은 과하게 해석했다.)

### 11-5. 판정과 한계

**혼합 DPI가 유력한 변수라는 것은 지지되었다.** 드리프트가 100% 보조 모니터에만 국한된다는 것은 §11-3의 위치 기반 오인과 정합한다.

**§12-A2에서 최소 폭 클램프 기전이 확인되어 이 가설은 대체되었다.** 아래 §12 참조. §11-5에서 "+42px의 산술이 설명되지 않는다"고 한 지적은 정당했으나, 배율이 **창 크기**가 아니라 **최소 트랙 크기**에 곱해진다고 보면 해소된다.

**여전히 증명되지 않은 부분:**
- Chromium/Electron이 실제로 어떤 API로 배율을 정하는지는 **소스를 검토하지 않았다.**
- 표본이 **창 1개 × 3회**였다. 창 종류·프로필·확장 프로그램 대조가 없다.
- Slack이 새지 않는 이유는 **확인하지 않았다.** Electron 쪽에 해당 수정이 있을 수 있다는 것은 가설이다.
- 주/보조 구분 자체가 변수일 가능성은 배제되지 않았다(§12-B1로 판별 가능).

### 11-6. 다음 판별 실험 (미실행)

§12-A1/A2가 수행되어 §12에서 확인되었다. 남은 설정 변경 실험은 **표시 설정이 바뀌어 사용자 승인 없이 진행하지 않았다.**

1. **DEL을 주 모니터로 지정**하고 배치도에서 노트북을 왼쪽에 배치. 최소화 창이 "주 모니터"로 판정되든 "가장 왼쪽"으로 판정되든 100% 모니터가 된다. → 최소→복원 3회.
2. **배율 통일.** Win+P → "두 번째 화면만"으로 노트북 화면을 끔. → 드리프트가 사라지면 혼합 DPI 확정.

교차 대조군:

| 조건 | 판별 대상 |
|---|---|
| Edge | Chromium 코어 문제면 동일 재현 |
| Chrome Beta/Canary | 특정 버전 문제면 해결 가능 |
| `--user-data-dir` 신규 프로필 | 프로필/확장 프로그램 문제 배제 |

**Edge도 재현되면 Chromium 코어 버그이므로 crbug 등록이 가능하다.** Canary에서만 사라지면 업데이트 대기, 신규 프로필에서만 사라지면 프로필/확장 문제다.

## 12. 최소 폭 클램프 가설 — 검증 (개정 3에서 추가)

### 12-1. 가설의 출발점

§11-5의 반박("배율 오인이면 2배나 절반이어야 하는데 42px다")은 **오인된 배율이 창 크기에 곱해진다고 가정**했다. 배율이 **최소 창 크기(`WM_GETMINMAXINFO`의 최소 트랙 크기)** 에 곱해진다면 결과가 달라진다.

창이 최소 크기보다 좁으면 Windows는 복원 시 최소 크기까지 키운다. 즉 드리프트는 **증가가 아니라 하한 clamps** 이다.

이 가설이 맞으면 다음이 모두 성립해야 한다.

| 예측 | §11 데이터와 일치 |
|---|---|
| zone 폭 974 < 잘못 계산된 최소 폭 → 그 최소 폭까지 증가 | +42 (974→1016) |
| 높이 1039는 최소 높이보다 크므로 불변 | 높이 1039 고정 ✓ |
| 좌측 고정·우측만 확장 | 최소 크기 리사이즈 ✓ |
| 한 번 변한 뒤 고정 (누적 아님) | 하한이므로 수렴 ✓ |
| 200% 모니터에서는 창이 최소폭보다 커서 무영향 | 2800 ≫ 최소 ✓ |
| 복원 후에는 창이 화면 위에 있어 배율 정상이므로 되돌릴 수 있음 | WPM 작동 ✓ |

### 12-2. A1 — 라이브 최소 폭 측정

WPM과 PowerToys(FancyZones)를 **모두 정지**시킨 뒤, `SetWindowPos` 직후 OS가 적용한 폭을 읽었다(96 DPI = 100% 모니터 위).

| 요청 폭 | 실제 적용 폭 |
|---|---|
| 100 | 516 |
| 300 | 516 |
| 400 | 516 |
| 450 | 516 |
| 500 | 516 |
| 508 | 516 |
| 520 | 520 |
| 600 | 600 |

**100% 모니터에서의 라이브 최소 폭 = 516.** 508이 아니라 **516**이다(가설은 508로 추측했으나 실제값과 다르다 — §12-5 참조).

### 12-3. A2 — 폭 스윕 (교란 제거)

WPM·FancyZones 정지 상태에서, DEL(100%)에 자유 배치로 폭을 바꿔 가며 최소→복원을 **각 1회** 수행했다. §11-4의 "FancyZones 배치 대 자유 배치" 교란과 "창 1개" 교란이 여기서 해소된다.

| 요청 폭 | 라이브 폭 | 복원 후 폭 |
|---|---|---|
| 700 | 700 | **1016** |
| 900 | 900 | **1016** |
| 1000 | 1000 | **1016** |
| 1015 | 1015 | **1016** |
| **1017** | 1017 | **1017** |
| 1100 | 1100 | 1100 |
| 1300 | 1300 | 1300 |

**결정적 결과: 폭 1016에서 뚜렷한 계단 함수.** 1016 미만은 복원 시 1016으로 올라가고, 1017 이상은 전혀 손대지 않는다.

이것은 **배율 오인이 크기 자체에 곱해지면 나오는 비례 오차와 형태가 다르다.** 비례 오차라면 폭에 따라 오차량이 연속적으로 변해야 하지만, 최소 크기 클램프는 **하한**이므로 정확히 이런 계단 함수를 만든다. 형태가 일치한다.

### 12-4. 가설로 설명되지 않는 잔여 현상

**`1554x1290`은 이 가설로 설명되지 않는다.** 높이가 1039 → 1290으로 변하므로 폭 클램프만의 효과일 수 없다. §2-2, §2-5, §2-7에서 재시작 직후 나타나는 별개 상태로 보인다.

**주의:** §12-A2는 1016만 재현했고 1554는 나오지 않았다(창을 여러 폭으로 재배치한 상태). **1554가 지금도 재현되는지는 별도로 확인하지 않았다.** 미해결.

### 12-5. 산술상 남는 불일치

- 가설의 추정: 최소 폭 `508` × 2 = `1016`
- 실측 라이브 최소 폭: **`516`**
- `516 × 2 = 1032` ≠ `1016` (차이 16)
- `1016 / 2 = 508` = `516 − 8`

**8px 차이가 남는다.** 이는 투명 테두리(measurement상 좌우 각 7px)와 관련된 것으로 보이지만, **정확히 확인하지 않았다.** 이 불일치가 해소되기 전까지 "Chrome의 최소 폭이 508"이라는 수치는 확정된 값이 아니다. **확인된 것은 임계값 1016과 라이브 최소 폭 516이라는 두 사실뿐이다.**

### 12-6. 실용적 함의

**zone 폭이 1017 이상이면 Chrome은 드리프트하지 않는다.**

| 레이아웃 (1920 작업영역) | zone 폭 | Chrome 안전 여부 |
|---|---|---|
| 1열 (전체) | 1920 | 안전 |
| 2열 균등 | 960 | **드리프트** |
| 3열 균등 | 640 | **드리프트** |
| 4열 균등 | 480 | **드리프트** |

작업영역 1920에서는 균등 다분할이 **어떤 개수든** zone 폭이 1017을 밑돌기 때문에 이 문제가 구조적으로 발생한다. 즉 **레이아웃 선택으로는 2/3/4분할 모두 회피 불가**하다. 이는 §5의 WPM 우회가 필요한 직접적 이유다.

또한 이 하한은 **앱별로 다르다.** Slack은 최소 폭이 더 작아 972 폭에서 문제없이 유지된다(§5에서 3회 확인). 따라서 1016은 Chrome 한정 값이며, 다른 앱의 최소 폭은 별도 측정이 필요하다.

### 12-7. 가설이 맞을 때의 해결 순서

> **개정 4에서 수정:** 1번(주 모니터 지정)은 §13 실험에서 **기각**되었다. 조건은 "가장 왼쪽"이어야 한다.

1. ~~**100% 모니터를 주 모니터로 지정**~~ → **실패(§13-2).** 주 모니터 조회는 쓰이지 않는다.
1. **[신규] 100% 모니터를 가장 왼쪽으로 배치** (노트북을 그 오른쪽으로). 배율이 100%로 정확해져 최소 폭이 516으로 내려가므로 974 > 516 이 되어 클램프가 발생하지 않아야 한다. **검증 완료(§14-2).** WPM 없이도 크기가 고정됨을 확인했다.
1. **배치 변경이 불가하면 WPM 유지.** §5에서 검증됨. zone 폭을 1017 이상으로 잡아도 이 환경의 균등 다분할에서는 불가(§12-6).

### 12-8. 미수행 실험

| # | 실험 | 판별 대상 | 상태 |
|---|---|---|---|
| B1 | DEL을 주 모니터로 지정 + 노트북을 왼쪽에 배치 | 주/보조 구분 vs 배율 | **표시 설정 변경 필요 — 미수행** |
| B2 | Win+P → "두 번째 화면만" | 배율 통일 시 드리프트 소멸 여부 | **표시 설정 변경 필요 — 미수행** |
| C1 | Edge | Chromium 코어 문제 시 동일 재현 → crbug 등록 가능 | 미수행 |
| C2 | Chrome Beta/Canary | 특정 버전 문제 시 업데이트로 해결 | 미수행 |

**§12-A2에서 임계값이 확인되었으므로 가설은 지지된다.** 다만 §12-5의 산술 불일치와 §12-4의 1554 미해결이 남아 있다. B1/B2는 사용자 승인 없이 표시 설정을 바꾸지 않아 실행하지 않았다.

## 13. 주 모니터 지정 실험 (개정 4에서 추가) — 가설 기각

### 13-1. 실험

§12-7의 해결 순서 1번, 즉 **100% 모니터를 주 모니터로 지정**하는 실험을 수행했다. 자동화(`ChangeDisplaySettingsEx`)는 `DISP_CHANGE_FAILED`(-4)로 실패하여 사용자가 설정 화면에서 직접 변경했다.

변경된 배치:

| 디스플레이 | 위치 | 크기 | DPI | 역할 |
|---|---|---|---|---|
| DISPLAY2 (DEL) | `0,0` | 1920x1080 | 96 | **PRIMARY** |
| DISPLAY1 (노트북) | `-2880,-228` | 2880x1800 | 192 | 가장 왼쪽 |

Chrome 창은 DEL 위에 있고, 측정 시 WPM·PowerToys를 정지시켜 순수하게 했다. DEL 작업영역은 `0,0 1920x1032`로 측정됐다.

### 13-2. 결과 — 임계값이 변하지 않았다

| 요청 폭 | 라이브 폭 | 복원 후 폭 |
|---|---|---|
| 400 | 516 | **1016** |
| 500 | 516 | **1016** |
| 516 | 516 | **1016** |
| 600 | 600 | **1016** |
| 700 | 700 | **1016** |
| 900 | 900 | **1016** |
| 1000 | 1000 | **1016** |
| 1015 | 1015 | **1016** |
| **1017** | 1017 | **1017** |
| 1100 | 1100 | 1100 |

zone 폭 확인:

```
before : 0,0 974x1032
restore: 0,0 1016x1032   ← 여전히 클램프됨
```

**§12-3의 결과와 완전히 동일하다. 임계값 1016, 하한 구조, 계단 함수 모두 그대로다.**

**따라서 "주 모니터 지정"은 해결책이 아니다.** §12-7의 해결 순서 1번은 **기각**한다.

### 13-3. 전제 직접 측정 — 위치 기반이라는 확정

가설이 왜 실패했는지 확인하기 위해, 최소화된 위치에 대한 **위치 기반 조회**를 직접 실행했다.

| 질의점 | 해석되는 모니터 | DPI |
|---|---|---|
| **(-32000,-32000)** (최소화 위치) | `(-2880,-228) 2880x1800` = **노트북** | **192 (200%)** |
| (0,0) | `(0,0) 1920x1080` = DEL | 96 (100%) |
| (-2000,-200) | 노트북 | 192 |
| (-2800,0) | 노트북 | 192 |

**창이 실제로 있는 DEL이 아니라, 가장 왼쪽에 있는 노트북(200%)이 나온다.**

이것이 §12-3 실험이 실패한 이유다. Chromium은 **주 모니터를 조회하지 않고, 창의 위치로 모니터를 결정한다.** 최소화 위치는 유효하지 않아 가장 왼쪽 디스플레이로 해석되고, 따라서 배율이 항상 200%로 산출되어 최소 폭이 2배(≈1016)로 부풀어 오른다.

§11-3에서 `MonitorFromWindow`(HWND 기반)는 정상이라고 관측한 것과 **모순되지 않는다.** 문제는 HWND 기반이 아니라 **위치 기반**이다.

### 13-4. 예측의 수정

초판 §11-6은 "DEL을 주 모니터로 지정하고 노트북을 왼쪽에 두면, 주 모니터든 가장 왼쪽이든 100% 모니터가 된다"고 예측했다. **이 예측은 틀렸다.**

> **정정:** 위 문구는 방향이 모호했다. §13이 실제로 시험한 조건은 **"노트북이 가장 왼쪽"** 이었다. 의도한 조건("DEL이 주 모니터이자 가장 왼쪽")은 §14에서 별도로 검증했다. §13은 실패한 조건의 시험이 아니라, **주 모니터와 가장 왼쪽이라는 두 변수를 분리시킨 실험**이었다. 이 분리가 §13-2(무효)와 §14-2(유효)를 만든 근거다.

노트북이 가장 왼쪽에 있으면, 최소화 위치 `(-32000,-32000)`는 노트북으로 해석되므로 **가장 왼쪽 기준은 200%다.** 두 기준이 서로 다른 답을 준다. 실험 결과는 "위치 기준"을 지지한다.

### 13-5. 올바른 조건과 남은 검증

| 조건 | 위치 조회 결과 | 예상 임계값 | 974 결과 | 상태 |
|---|---|---|---|---|
| 노트북 주 + 왼쪽 (원래) | 노트북 200% | 1016 | 클램프 | **측정됨** |
| DEL 주, 노트북 왼쪽 | 노트북 200% | 1016 | 클램프 | **측정됨 (§13-2)** |
| **DEL이 가장 왼쪽** | DEL 100% | ≈516 | **유지** | **미검증** |

**필요조건은 "주 모니터"가 아니라 "가장 왼쪽"이다.** DEL을 가장 왼쪽으로 옮기면(노트북을 DEL 오른쪽으로) 배율이 100%로 정확히 산출되어 최소 폭이 516으로 내려가고, 974 > 516 이므로 클램프가 발생하지 않아야 한다.

**이 예측은 아직 검증하지 않았다.** 배치 변경이 한 번 더 필요하며, 검증하면 WPM 없이도 문제가 사라질 수 있다.

### 13-6. 이 실험이 바꾼 것

- §12-7 해결 순서 1번(주 모니터 지정) → **기각**
- §11-6의 예측 → **기각**(이유 §13-4)
- 기전 이해 → **"주 모니터"가 아니라 "가장 왼쪽 디스플레이의 배율"로 확정**
- WPM의 필요성 → DEL을 왼쪽으로 옮겨 해결되면 WPM이 불필요해질 수 있음

## 14. DEL을 가장 왼쪽으로 — 가설 최종 확인 (개정 5에서 추가)

### 14-1. 실험

§13-5가 예측한 조건, 즉 **100% 모니터를 가장 왼쪽으로 배치**하는 실험. 사용자가 노트북을 DEL 오른쪽으로 옮겼다.

| 디스플레이 | 위치 | 크기 | DPI | 역할 |
|---|---|---|---|---|
| DISPLAY2 (DEL) | `0,0` | 1920x1080 | 96 | **가장 왼쪽 + PRIMARY** |
| DISPLAY1 (노트북) | `1920,-446` | 2880x1800 | 192 | 오른쪽 |

### 14-4. 확정된 기전

세 번의 배치 조건을 Controlled comparison으로 정리하면 모든 관측이 일관된다.

| 조건 | 가장 왼쪽 모니터 | 위치 조회 배율 | 복원 시 최소 폭 | 974 결과 |
|---|---|---|---|---|
| 노트북 주+왼쪽 | 노트북 200% | 2.0 | ≈1016 | 클램프 |
| DEL 주, 노트북 왼쪽 | 노트북 200% | 2.0 | ≈1016 | 클램프 |
| **DEL 왼쪽** | **DEL 100%** | **1.0** | **516** | **유지** |

확정된 사실:

1. Chromium은 un-minimize 시 **창 위치로 디스플레이를 결정한다.** 주 모니터는 조회하지 않는다(§13-2).
2. 최소화 위치 `(-32000,-32000)`는 유효하지 않아 **가장 왼쪽 디스플레이**로 해석된다(§13-3, §14-1).
3. 그 배율을 최소 트랙 크기에 곱하므로, 200%일 때 최소 폭이 2배로 부풀어 **하한 1016**이 생긴다(§12-3, §14-2).
4. 가장 왼쪽이 100%면 배율이 정확해져 하한이 516(실제 최소 폭)으로 내려가고, zone 폭 974는 그보다 넓어 클램프되지 않는다.
5. **왼쪽 좌우 비대칭(위치 유지·폭만 변경), 누적 아님, 1회 후 고정**이라는 §1의 모든 관측이 이 기전에서 나온다. 최소 크기 리사이즈는 좌측을 고정하고 오른쪽으로 늘리며, 하한이므로 수렴한다.

### 14-5. 해결

**100% 모니터를 가장 왼쪽에 배치한다.** 배치 변경만으로 WPM 교정 없이도 문제가 완전히 사라진다.

WPM이 할 일은 없어졌다. 남은 선택지는 다음이며, **아직 결정하지 않았다.**

- (a) WPM에서 zone 교정 기능(§12 이전에 추가한 부분)을 제거하고, 자유 창 위치/크기 관리만 남긴다
- (b) WPM을 통째로 종료한다
- (c) 그대로 둔다 (동작하지만 불필요한 개입이 남아 있음)

### 14-6. 재발 조건

이후 노트북이 가장 왼쪽으로 다시 가면(노트북을 외장으로 쓰거나, 배치를 바꾸거나) **즉시 재발한다.**

> **폴백 1줄:** 해결 수단은 셋뿐이다 — (1) 100% 모니터를 가장 왼쪽으로 옮긴다, (2) Chrome을 **폭 1017 이상인 zone**에만 넣는다(1920 작업영역에서는 균등 2/3/4분할 불가, **1열 전폭 1920만 가능**), (3) WPM zone 교정을 복원한다(`wpm_v6.ahk.with-zone-correction` 백업).

정확한 판정 기준은 "가장 왼쪽"이 아니라 **"(-32000,-32000)에 가장 가까운 디스플레이"** 다. 두 기준은 현재 배치에서 같지만, 디스플레이를 위아래로 쌓으면 갈릴 수 있으므로 **100% 모니터를 왼쪽(그리고 위쪽)에 두는 것으로 기억하면 안전하다.** 확인된 것은 Windows API의 응답이며, Chromium 내부 계산은 소스를 보지 않았다.

### 14-7. §13 이후 남은 미해결

- **§12-5의 산술 8px 불일치:** 실측 라이브 최소 폭 516에 대해 하한이 1016이므로 비가 1.969배다. 2배가 아니다. 투명 테두리 관련로 추정되나 확정하지 않았다. §14에서 하한이 516이 되어 관측 범위에서 사라져, 이 불일치는 §12/§13의 배치에서만 관측된다.
- **§12-4의 1554x1290:** 최소 폭 클램프로는 설명되지 않는다(높이까지 변함). **이 배치에서 재현 여부를 확인하지 않았다.** 미해결.
- Chromium 소스 미검토. 위 기전은 Black-box 관측으로만 확정했다.

### 15-5. 현재 상태와 남는 문제

**이 제거는 드리프트를 고친 것이 아니다.** 원본 배치로 되돌린 시점에 1016 하한이 되살아났고, 균등 2/3/4분할 zone에서 Chrome은 복원 시 다시 늘어납니다. 제거한 것은 **증상을 덮던 코드**이고, 원인은 여전히 있습니다.

§14-2는 하한이 **배치에서** 사라짐을 보였고, §12-6은 균등 다분할에서는 어떤 개수든 1920 작업영역을 나눈 zone 폭이 1017을 밑돈다고 계산했다. 따라서 **레이아웃 설정만으로 이 드리프트를 없앨 수 있는 경우(1열 전폭)는 Chrome을 단독으로 쓸 때뿐**이며, 다른 앱과 zone을 공유하는 2/3/4분할에서는 구조적으로 불가능하다.

진짜 해결은 §14-6의 세 가지 중 하나를 고르는 것이다. (1)은 배치를 바꾸는 것이고, (3)은 방금 제거한 코드를 되돌리는 것이다. **WPM 교정 없이 가능한 것은 (2)의 제한된 경우뿐이며, 그것도 Chrome 전용 1열이어야 한다.**

## 16. WM_GETMINMAXINFO 직접 관측 (실험 결과 문서 참조)

별도 문서에 전문이 있다: `Chrome_창크기_DRIFT_실험결과_WM_GETMINMAXINFO.md`

### 확인됨 — 200% 조건에서만 `ptMinTrackSize.x`가 1016

| Experiment | 최소화 위치 판정 | DPI | 샘플 | minTrack=1016 | restore 폭 |
|---|---|---:|---:|---:|---:|
| A (노트북 왼쪽) | 노트북 | 192 | 201,195 | **9** | 1016 |
| B (DEL 왼쪽, 노트북 주 화면 유지) | DEL | 96 | 194,771 | **0** | 974 |

전이 순서(3회 동일, 과도 각 1~2 ms):

```
최소화  width=314   minTrack.x=516
        width=314   minTrack.x=1016   ← 최소화된 채로 팽창
복원    width=1016  minTrack.x=516    ← 1016에 클램프된 뒤 복귀
```

**1016은 복원 결과에서 파생된 숫자가 아니다.** 복원 **이전**, 창이 최소화된 상태에서 `WM_GETMINMAXINFO.ptMinTrackSize.x`가 실제로 1016이며, 그 값이 폭에 적용된 뒤 516으로 돌아온다.

### `GetDpiForWindow`는 그 경로가 아니다

`minTrack.x = 1016`이던 **9개 샘플 전부**에서 `GetDpiForWindow`는 **96**이었다. 전체 395,966개 샘플도 96뿐이다. 두 값이 같은 순간에 다르게 나타나므로 `minTrack = f(GetDpiForWindow)`는 성립하지 않는다.

### 갱신된 관점

- §4의 "Chromium이 배율을 구하는 API는 미확정"은 그대로 유지하되, `GetDpiForWindow`는 **배제**되었다.
- "배율이 최소화된 창의 위치에서 결정된다"는 §13-2/§14-2/§16-1로 반복 검증되었다.
- 배율이 **최소 트랙 크기에만** 곱해진다는 해석은 `maxSize`/`maxTrack`/`maxPos`가 Chrome이 채우지 않는다는 관측과 함께 미확인으로 남는다.

### 미해결 분리

| 현상 | 상태 |
|---|---|
| 1016 하한 | **원인 범위가 강하게 검증됨** (배치 통제로 소멸 확인) |
| 1026 (재시작 직후) | **별도 미해결.** `minTrack.x`(516)와 다른 값이며 zone 배치 전에만 관측 |
| 1554x1290 | **별도 미해결 outlier.** A/B 각 3회에서 재현되지 않음 |

### 관측 방법론 메모

동기 `SendMessage`로는 과도 구간(~1–2 ms)을 볼 수 없다. 첫 시도에서 36,135 샘플을 찍었으나 1016은 0회였다. **별도 프로세스 연속 샘플링 + 별도 프로세스 트리거**로만 포착했다.

## 17. monitor 판정 동시 관측 — 가설 수정 (실험 결과 문서 참조)

별도 문서: `Chrome_창크기_DRIFT_실험결과_monitor판정동시관측.md`

### 확인됨

| 항목 | A (200% 왼쪽) | B (100% 왼쪽) |
|---|---|---|
| 샘플 | 155,639 | 182,292 |
| `minTrack` = 1016 | **9** | **0** |
| width = 1016 | 134,546 | **0** |
| `MonitorFromWindow` 가 200% 모니터로 전환 | **11 샘플** | **0** |
| 전환 ↔ 1016 발생 중첩 | **9 / 9** | 해당 없음 |
| `MonitorFromPoint` | 192 고정(전 구간) | 96 고정(전 구간) |
| `GetDpiForWindow` | 96 고정 | 96 고정 |
| awarenessCtx / awareness | 34 / 2 고정 | 34 / 2 고정 |
| `GetDpiForSystem` | 96 고정 | 96 고정 |

A에서 `MonitorFromWindow`가 200% 모니터를 반환한 11개 샘플 중 **9개가 `minTrack=1016`과 정확히 중첩**했다. 나머지 2개는 전이 직전이다. B에서는 최소화 중에도 `MonitorFromWindow`가 DEL@96을 유지했고 1016은 0회였다.

### 가설 수정 — 위치 직접 조회 가설은 폐기

**"Chromium이 `(-32000,-32000)` 위치를 직접 조회한다"는 설명을 버린다.**

A에서 `MonitorFromPoint(-32000,-32000)`는 155,639 샘플 **전부** 192를 반환했고 **한 번도 변하지 않았다.** 1016이 아닌 155,630개 순간에도 192였다. 따라서 그 반환값은 `minTrack`를 설명하지 못한다.

**수정된 설명:** Windows가 **최소화된 창을 200% 모니터 소속으로 보고**하고, Chromium이 그 소속에 따라 최소 트랙 폭에 배율을 적용한다. 트리거는 `MonitorFromWindow`의 답이 바뀌는 순간이다.

### 측정 방법론상 두 조건 (재현에 필요)

1. **프로세스 DPI 인지 필수.** `GetDpiForMonitor`는 호출 프로세스가 per-monitor aware가 아니면 모든 모니터에 96을 반환한다. 모니터 위의 창으로 `GetDpiForWindow`를 조회하는 방식(모니터→DPI 맵)으로 대체해야 올바른 192/96이 나온다.
2. **과도(~1–2 ms) 포착에 별도 프로세스 필요.** `ShowWindow`가 동기 호출이므로 동일 스레드에서는 반드시 놓친다.

### 미확정 추가

Chromium이 실제로 `MonitorFromWindow`를 호출하는지(내부 미검토), 배율이 최소 트랙 폭의 어느 부분에 곱해지는지, 최소화 구간 진입/이탈 트리거가 무엇인지.
