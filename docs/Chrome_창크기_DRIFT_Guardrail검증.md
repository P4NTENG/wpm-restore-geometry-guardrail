# Guardrail 검증 실험 결과

**실시:** 2026-09-29
**목적:** DPI 내부 구현을 알지 못해도 1016 drift를 감지·차단할 수 있는가

## 1. 실험 목적

"1016이 왜 생겼는가"가 아니라, **"WPM이 1016 drift를 안정적으로 감지하고 차단할 수 있는가"** 를 검증한다.

## 3. WM_DPICHANGED — 관측 불가

`WM_DPICHANGED`는 임의 윈도우 메시지다. `SetWinEventHook`는 커버하지 않고, 관측하려면 대상 프로세스에 훅을 설치하거나 서브클래싱해야 하는데 둘 다 금지 항목이다.

**관측 경로가 존재하지 않는다.** 따라서 "미발생"이 아니라 **"관측 불가"**로 기록한다.

귀결(지시서 §17)에 따라: **guardrail 트리거로 `WM_DPICHANGED`를 쓸 근거가 없다.** 실제로 관측했다 해도 "1016을 발생시켰다"고 결론내리지 않았을 것이므로, 사용하지 않는 판단은 동일하다.

## 4. MINIMIZEEND와 geometry 관계 (실험 B)

C# 호스트, 221,647 샘플 / 3회 반복, 표본 42–93 µs.

| 사이클 | MINIMIZESTART | 전환 시작 | MINIMIZEEND | 전환 위치 |
|---:|---:|---:|---:|---|
| 1 | 2141.405 | 2558.134 | 2569.115 | START **+416.7 ms**, END **−11.0 ms** |
| 2 | 5206.474 | 5624.545 | 5636.708 | START **+418.1 ms**, END **−12.2 ms** |
| 3 | 8277.924 | 8684.153 | 8712.521 | START **+406.2 ms**, END **−28.4 ms** |

**최소화 상태 400 ms 이상 동안 변화가 없다.** 전환은 복원 직전 1–2 ms에만 발생한다. 최소화가 트리거가 아니다.

`MINIMIZEEND` 이벤트는 실제 복원보다 7–28 ms 늦게 기록된다(out-of-context 큐 전달 지연). 권위 있는 시각은 이벤트의 `sysTime`이며, 실제로 창이 1016이 된 시점은 이벤트보다 앞선다.

## 5. Guardrail 구현 (지시서 §9 그대로)

```
restore
  → GetWindowRect
  → expected zone 비교
  → 불일치면 SetWindowPos(expected)
  → 재조회로 검증
  → 1~2 초 관찰하여 re-drift 확인
```

DPI 추론 없음, 1016 상수 보정 없음. 실제 HWND geometry + 예상 zone geometry만 사용.

## 8. False positive / negative

### 정상 zone 유지 시 개입 없음 — 확인

1016 / 1017 / 1044 에서 **18 사이클, 개입 0회**. geometry가 맞으면 아무것도 하지 않는다.

### ⚠ 수동 resize 후 복원 시 오작동 — 확인됨 (미해결)

| 조건 | 결과 |
|---|---|
| guardrail 없이, 사용자가 폭 1150으로 resize → 3회 복원 | `1150x1039` 유지. **드리프트 없음** (1150 > 1016) |
| guardrail ON (expected 974), 동일 시나리오 | `1016` 로 복귀 → **974 로 교정** |

**문제:** 사용자가 명시적으로 1150으로 resize한 창을 guardrail이 974로 되돌린다. 사용자의 선택을 덮어쓴다. 지시서 §15가 경고한 그 오작동이다.

**원인:** 비교 기준이 **저장된 zone**이라, 사용자가 zone 밖으로 resize하면 "불일치"로 판정된다.

**권장 수정 — 비교 기준을 최소화 직전 geometry로:**

```
최소화 직전 width 기록
  ↓
복원 후 width 비교
  → 이전과 같으면 아무것도 하지 않음
  → 달라졌으면(증가) 최소화 직전 값으로 복구
```

이 방식은 1016 상수도, zone 저장소도, DPI도 쓰지 않는다. 사용자가 resize한 값이 복원 후 그대로 유지되므로 위 false positive가 사라진다.

**이 변형은 아직 테스트하지 않았다.** 아래 구현안 제안은 이 근거 위에 있으나 검증 전이다.

## 11. 최종 설계안 (검증 전)

```
기록: 최소화 직전 geometry (hwnd별, 메모리)
  ↓
복원 감지 (MINIMIZEEND 또는 sweep 의 iconic→normal 전이)
  ↓
GetWindowRect 비교
  ├─ 이전과 동일 → 아무것도 안 함
```

## 13. 미확정

- Chromium/Windows 내부에서 1016이 만들어지는 원인
- `WM_DPICHANGED` 발생 여부 (관측 불가)
- `WM_SIZE` / `WM_WINDOWPOSCHANGED` flags (외부 관측 원천 불가)

- 사용자가 zone 밖으로 resize한 뒤의 의도적 유지 동작

| DEL 자유 배치 900x700 | 6/6 | 6/6 | 0/6 | 0/6 | `1016x700` | **900x700** |

**잘못된 모니터로 순간 이동한 사례: 0건.** 교정 후 좌표는 항상 기록된 baseline과 일치했다.

- 1b는 **zone이 아닌 자유 배치**에서도 동일하게 동작한다. 하한은 폭에만 걸리고 높이는 그대로였다(`1016x700`).
- 1c는 **테스트가 오염**되었다. 100% 모니터에서 200% 모니터로 `SetWindowPos`를 걸 때 Windows가 DPI 비율로 크기를 스케일링해(1200 → 2400) 요청과 달랐고, 그 상태를 baseline으로 잡았다. guardrail은 그 baseline을 그대로 유지했다(개입 0).

**설계상 안전성의 근거:** baseline은 **최소화 직전**에 기록된다. 최소화된 창은 사용자가 움직일 수 없고, 사이클 안에서 monitor가 바뀔 경로가 없다. "모니터 A 좌표를 모니터 B에 적용하는" 시나리오는 구조적으로 발생하지 않는다. 단, 구현에서 baseline을 **hwnd별 캐시로 사이클을 넘어 유지**하면 이 안전성이 사라지므로, 캐시 수명을 별도로 검증해야 한다.

### 14-3. 부수 발견 — 1026의 정체

시작 관측 중 `minTrack.x = 1026`이 166,009샘플 전부에서 관측되어, 별도로 확인했다.

|---|---:|---:|

## 16. 통합 시 유의점

1. **baseline은 사이클 안에서만 살아야 한다.** hwnd별 영구 캐시가 되면 교차 모니터에서 낡은 좌표를 적용할 수 있다. 저장 시점은 "최소화 직전", 폐기 시점은 "복원 후 비교 완료".
2. **비교는 4좌표 전부** 해야 한다. 폭만 비교하면 1b 케이스(높이 700 유지, 폭만 클램프)에서 정상 판정된다.
3. **이미지 배율에 의존하지 않는다.** `tl2.exe`가 DPI 비인지 프로세스라 2400을 1200으로 읽는 식의 가상화가 있으나, guardrail 대상 프로세스는 PerMonitorV2다. 통합 시 DpiInit 상태를 확인할 것.
4. **zone 여부는 판정에 쓰지 않는다.** 자유 배치 창도 동일하게 보호된다(1b).

위 1~16절은 독립 하네스(`gr.exe`)에서 얻은 **실험 결과**다.

## 17. 통합된 것

설계 이름은 "Chrome 1016 픽스"가 아니라 **Restore Geometry Invariant Guardrail** 이다.
Chrome나 Chromium의 내부 원인을 다루지 않는다. Windows의 HWND lifecycle과 geometry API,
FancyZones의 기존 spatial model을 그대로 쓰고, 그 사이에서 restore 순간의 geometry 불변식만 지킨다.

### 17-1. 통합 위치

새 polling loop를 추가하지 않았다. 기존 `Sweep()` 안, 창을 만나자마자 그 창의 현재 상태를
확인하는 지점에 넣었다. born 판정, zone 판정, INI 기록 판정보다 **앞**에 두었다.
guardrail은 그 창의 "지금 무엇인가"에 관한 것이지 이 매니저가 파일에 무엇을 써 두었는지에 관한 것이
아니기 때문이다.

```
Sweep()
  for hwnd in EnumTopWindows()
    IsUsableWindow / IsMoving / GetWindowRect
+   GuardTick(hwnd, rect)        ← 삽입 지점 하나
      baseline 있으면 비교 후 보정
      없으면 현재 geometry 를 mirror 에만 갱신
    born 판정
    IsFancyZoneWindow
    Reconcile
```

삽입은 이 한 줄뿐이다. 이를 지우면 `Sweep`은 guardrail이 없던 그 상태로 정확히 돌아간다.

### 17-2. lifecycle

```
IDLE ──MINIMIZE──> MINIMIZE_PENDING(baseline 캡처) ──> MINIMIZED
                                                    │
                                                    ↓
IDLE <──COMPLETED(baseline 폐기) <──CORRECTING <──VALIDATING <──RESTORE_PENDING
```

`GuardIconic` 은 직전 sweep 에서 iconic 이었는지만 기억한다(1비트). `GuardBaseline` 은
캡처된 그 한 사이클의 사각형 하나만 담는다. `GuardLast` 는 창이 minimize 되어 있지
않는 동안 매 sweep 에 실제 geometry 로 덮어쓰이는 **관측값**이며, 정책이 아니다.

영구 `HWND → 기대 geometry` 맵은 존재하지 않는다. 그것이 cross-monitor 안전성의 근거다.
창이 사람이 옮겼는데 옛 위치로 되돌려 놓는 일이 구조적으로 불가능하다.

`WinEventDestroy` 에서 세 맵을 모두 지운다. 실제로 이건 필요했다. 실험 중 Chrome 이 주창
hande 를 여러 번 새로 만들었고(`16517790 → 3605646 → 5509588 → 5636354`), 재활용된
handle 이 앞선 창물의 사각형을 물려받지 않아야 한다.

### 17-3. 규칙을 지킨다는 근거

| 금지 항목 | 상태 |
|---|---|
| dpi 조건문 | 없음 (`GetDpiForWindow` 을 guardrail 이 읽지 않음) |

## 22. 통합 2차 — `Sleep` 이 sweep 을 죽이고 있었다

사용자가 zone 등록을 마친 뒤 실제로 써 보니 **드디어 원래 증상이 재현**됐다.
그런데 처음엔 guardrail 이 못 고치는 것처럼 보였다. 추적해 보니 guardrail 이 아니라
**guardrail 이 `Sweep()` 안에서 `Sleep` 하고 있었다**는 것이었다.

### 22-1. 증상

zone(974)에 놓인 Chrome 을 최소화/복원하면 1016 으로 빠진다. 그런데 **1회 교정된 뒤
1016 이 새 baseline 으로 굳어버려** 이후로는 "1016 이 정상" 이 되어 개입이 멈췄다.

```
17:27:01 baseline captured rect=3833|422|974|1039
17:27:02 restore detected
17:27:02 geometry mismatch baseline=...974|1039 actual=...1016|1039
17:27:02 correction verified rect=3833|422|974|1039      ← 교정 성공
17:27:06 baseline captured rect=3833|422|1016|1039      ← ★ 4초 만에 1016
17:27:07 geometry match 1016                            ← 1016 을 정상으로 인정
```

### 22-2. 원인

§10 의 re-drift 재검증을 위해 `GuardTick` 안에 `Sleep(150)` 을 넣어 두었다.
`GuardTick` 은 `Sweep()` 안에서 호출된다. **`Sleep` 은 그 창만 기다리는 것이 아니라
스레드 전체를 멈춘다.** `Sweep` 를 깨우는 타이머도 이 함수가 반환하기 전에는 돌지
않으므로, 그 150ms 동안 **다른 모든 창도 함께 관리 대상에서 빠진다.**

증거는 로그에 있었다. 마지막 `sweep ok` 기록이 `17:27:16` 이었고, 그 뒤 3분간
`sweep ok` 가 한 건도 없었다. `tracked` 도 갱신되지 않았다.

그래서 시나리오는 이렇다.

```
교정 성공 (974)
→ Sleep 으로 sweep 150ms 정지
→ 그동안 Chrome 이 자기 값(1016)을 되돌림
→ 다음 sweep 이 1016 을 baseline 으로 캡처
→ 이후 "1016 = 정상" 으로 동작 종료
```

즉 guardrail 이 설계대로 동작했는데, **자기 재검증을 위해 다른 창을 포기하면서**
드디어 지켜야 할 순간을 놓쳤다.

### 22-3. 수정 (A안)

`Sleep` 을 제거했다. 정정은 곧바로 끝내고, 그 다음 사각형은 있는 그대로 기록한다.
이후 그 창이 움직이면 다음 sweep 이 그것을 "지금 있는 위치"로 읽고, 다음
minimize 사이클에서 그 새 위치를 baseline 으로 잡는다.

기다림을 넣지 않는 이유는 코드에 남겼다. sweep 안에서 잠자는 것은 이 창만
기다리는 게 아니라 **sweep 전체를 세우는 것**이기 때문이다.

`GuardSettleMs` 상수도 함께 제거했다. 쓰이지 않는다.

### 22-4. 수정 후 결과

동일한 조건(zone 974), 디버그 로그:

```

17:32:42 restore detected

```

| | 이전 | 수정 후 |

릴리스 빌드에서도 3/3 이 974 를 유지했다.

### 22-5. 검은 화면에 대해

사용자 관찰: 창을 이동시킨 뒤 최소화/복원하면 잠깐 검은 화면이 나온다.
원인으로 지목된 것은 **머신러닝 작업 중인 프로그램의 윈도우 리소스 부족**이었다.

WPM 이 원인이 아니라는 것은 정황으로만 확인되었고, 재현은 되지 않았다.
화면 루미넌스를 2ms 간격으로 샘플링해 restore 직후 3초를 잰 결과:

| 조건 | darkest run |
|---|---|

| WPM 가동 (Sleep 빌드) | 13, 23, 22, 25, 25 ms |
| WPM 가동 (Sleep 제거) | 21, 39, 53, 17, 72 ms |

WPM 을 켜도 꺼도 수치상 구분이 없고, 모두 눈에 띄게 깜빡일 정도(100ms 이상)는
없다. 초기의 181ms / 2447ms 는 최소화 사각형(`-32000,-32000`)을 샘플 영역으로
사용한 측정 오류였고, 프로브를 고쳐 재측정하면 사라졌다.

**결론: WPM 및 guardrail 의 영향으로 볼 근거가 없다.** 다만 이것은 재현 실패로
결론낸 것이지, 자원 부족 원인을 배제한 것은 아니다. 사용자가 ML 작업을 멈춘
상태에서 다시 보인다면 그때는 WPM 을 의심할 근거가 생긴다.

# 23. 통합 3차 — 이벤트 훅(B안)은 이 플랫폼에서 되지 않는다

빠른 최소화/복원에서 크기가 돌아오지 않는 버그가 있었다. 재현 결과:

| minimize→restore 간격 | 성공 | 실패 |
|---:|---:|---:|
| 50ms | 1/6 | 5/6 |
| 100ms | 0/6 | 6/6 |
| 150ms | 0/6 | 6/6 |
| 200ms | 4/6 | 2/6 |
| 300ms | 6/6 | 0/6 |
| 450ms | 0/6 | 6/6 |
| 600ms | 0/6 | 6/6 |
| 800ms | 6/6 | 0/6 |
| 1200ms | 6/6 | 0/6 |

성공 구간이 스윕 주기(700ms) 경계에서 끊긴다. 원인은 세 가지였다.

**1. 스윕이 minimize 를 못 본다** (100~200ms) — 사이클이 두 스윕 사이에 통째로 들어가
baseline 이 잡히지 않는다. 개입할 대상이 없다.

**2. 스윕이 복원 직후를 지나친다** (450~600ms) — restore 직후를 스윕이 스치면
1016 을 baseline 으로 받아들인다. "1016 = 정상" 이 되어 개입이 영구히 멈춘다.

**3. 스윕이 minimize 중에 본다** — 실제 복원이 아직인데 `-32000|-32000|314|50` 을
복원 후 사각형으로 읽고 거기에 baseline 을 적용한다. 아직 최소화 중인 창을
옮기는 것이니 교정이 아니다.

로그:
```
17:27:01 baseline captured  rect=3833|422|974|1039
17:27:02 geometry mismatch  baseline=...974|1039 actual=...1016|1039
17:27:02 correction verified rect=3833|422|974|1039      ← 교정 성공
17:27:06 baseline captured  rect=3833|422|1016|1039      ← ★ 4초 만에 1016
17:27:07 geometry match 1016                            ← 1016 을 정상으로 인정
```

## 23-1. B안 시도: `EVENT_SYSTEM_MINIMIZESTART` / `MINIMIZEEND`

스윕 주기 의존을 없애려면 minimize 의 두 끝을 시스템 이벤트로 받아야 한다.
이벤트 상수는 정확했다 (`MINIMIZESTART=0x0016`, `MINIMIZEEND=0x0017`),
훅 등록도 성공했고 `MINIMIZEEND` 는 정상적으로 도착했다.

**그런데 `MINIMIZESTART` 는 Chrome 창에 대해 발화하지 않았다.**

전체 실행 동안 3회. 사용자 클릭 최소화, `Win+D`, 타 프로세스의
`ShowWindow(SW_MINIMIZE)` — 어느 경로에서도 0회. `MINIMIZEEND` 는 같은 구간에
수십 회 왔다. `IsWindowVisible` 은 최소화 중에도 항상 true 였고
(`IsUsableWindow` 가 걸리지 않음), `IsIconic` 도 정상. 즉 문제는 이벤트 자체가
없다는 것이었다.

이는 `tl2.exe` 실험에서 이미 관측한 사실과 일치한다. 그때도 전환이
`MINIMIZEEND` **11~28ms 전**에 발생했고 `MINIMIZESTART` 는 신뢰할 수 없다고
결론 내렸다. 그 제약(§18: 이벤트 순서 재현 금지)을 잊고 B를 근본해로 제안한 것은
잘못된 판단이었다.

결과적으로 baseline 이 0 회 잡혀 `no baseline` 만 47 회 반복했고, 스윕 기반보다
나빴다. **B안은 철회하고 A안(스윕 + `GuardIconic`)으로 되돌렸다.** 실패 사유는
코드에 주석으로 남겼다.

## 23-2. `Sleep` 제거

§10 의 re-drift 재검증을 위해 `GuardTick` 안에 넣은 `Sleep(150)` 이 다른 버그의
원인이었다. `GuardTick` 은 `Sweep()` 안에서 호출되므로, `Sleep` 은 그 창만
기다리는 것이 아니라 **스레드 전체를 멈춘다.** `Sweep` 를 깨우는 타이머도 반환
전에는 안 돌기 때문에, 그 150ms 동안 다른 모든 창이 관리 대상에서 빠졌다.

증거: 마지막 `sweep ok` 기록이 `17:27:16` 이었고 그 뒤 3분간 한 건도 없었다.

`Sleep` 을 제거했다. 정정 직후의 사각형은 있는 그대로 기록하고, 그 창이
이후 움직이면 다음 스윕이 그것을 "지금 있는 위치"로 읽으며, 다음 minimize
사이클에서 새 위치가 baseline 이 된다. `GuardSettleMs` 상수도 함께 제거했다.

| | `Sleep` 있음 | 제거 후 |
|---|---|---|
| `sweep ok` | 17:27:16 에 멈춤 | 계속 동작 |
| 4 사이클 | 1회 교정 후 1016 고정 | **4/4 전부 974 유지** |

## 23-3. 창별 위치 분리 (파일 탐색기 겹침)

별개로, 파일 탐색기를 두 개 열면 두 창이 같은 좌표로 겹쳤다.

원인은 `GetWindowKey` 가 `proc|cls` 만 쓴 것이었다.

```ini
explorer.exe|CabinetWClass=...      ← 두 창이 키를 공유
```

두 번째 창이 첫째 좌표를 덮어쓰고, `Reconcile` 이 두 개 모두를 그 자리로
당긴다. `Zed.exe|Zed::Window`, `Code.exe|Chrome_WidgetWin_1` 도 같은 구조다.
guardrail 과 무관한 기존 설계 결함이었다.

수정은 슬롯 번호를 키에 넣는 것이다.

```
explorer.exe|CabinetWClass|1
explorer.exe|CabinetWClass|2
```

- `WindowSlot` — hwnd별 슬롯. 창이 살아 있는 동안 고정
- `WindowSlotNext` — `proc|cls`별 다음 슬롯 번호
- `WinEventDestroy` 에서 슬롯 반납 → 닫았다 reopen 하면 같은 슬롯 재사용

### 제목을 넣었다가 뺀 이유

처음에는 제목도 키에 넣었다. 두 탐색기 창은 폴더 이름이 다르니 그것으로
구별될 seemed. **틀렸다.** 창을 다른 폴더로 탐색하면 제목이 바뀌므로, 방문할
때마다 같은 슬롯 아래 새 기록이 쌓였다.

```ini
explorer.exe|CabinetWClass|1|프로젝트A - 파일 탐색기=3266|638|1013|743
explorer.exe|CabinetWClass|1|다운로드 - 파일 탐색기=3199|756|900|600
```

`Reconcile` 은 자기 제목이 아닌 기록까지 찾아 창을 끌어당겼다. 두 창이 서로의
자리를 계속 바꾸며 덮어썼다 — 고치려던 바로 그 증상이다.

제목을 빼고 **슬롯 번호만으로 식별**하도록 바꿨다. 슬롯은 WPM 이 그 프로그램을
처음 본 순서이고, 창이 살아 있는 동안 변하지 않으므로 자기가 갑자기 남의
기록을 찾을 일이 없다.

### 검증

| 항목 | 결과 |
|---|---|
| 두 창이 서로 다른 슬롯을 갖는가 | 1, 2 로 분리 |
| 한 창만 왕복해도 다른 창이 움직이나 | **움직이지 않음** |
| 창만 최소화/복원 | 자기 자리 복귀, 다른 창 불변 |

## 24. 남은 한계

빠른 최소화/복원(<300ms)은 여전히 고쳐지지 않는다. 스윕이 700ms 주기인 이상
구조적으로 불가능하다. 해법은 `EVENT_SYSTEM_MINIMIZESTART` 인데 이 빌드에서
그 이벤트가 오지 않는다.

| 간격 | 상태 |
|---:|---|
| 100~200ms | 미해결 — 스윕이 minimize 를 못 봄 |
| 300ms 이상 | 대부분 정상 |
| 450~600ms | 스윕 위상에 따라 불안정 |

이것은 현재 OS/앱 조합에서 이벤트를 신뢰할 수 없어서이며, 코드 안에서
우회할 수 없다. 문서화만 되어 있다.

# 25. 이벤트 경로 검증 — 앞선 서술의 정정과 남은 위험

## 25-1. 정정: 드리프트는 간격과 무관하게 매번 발생한다

§23의 gap별 표(120ms에서만 재현)는 샘플링 아티팩트였다. 이벤트 로그를
기준으로 하면 `mismatch`가 120/400/1500ms 전부에서 나온다. 즉 드리프트는
매 복원마다 발생하고, 앞선 "120ms에서만" 관측은 스윕이 복원 직후를
지나쳐 1016을 baseline으로 받아들인 경우였다. "스윕이 구조적으로 못 잡는
구간은 120ms뿐"이라는 프레임도 성립하지 않는다. 이벤트 경로는 모든
복원에 필요했다.

## 25-2. mirror의 소비자 (헤드라인과의 정합)

"스윕 역할: mirror 공급만"에서 mirror를 소비하는 곳은 `GuardCapture`다.
`MINSTART`에서 읽은 셸 값과 크기가 다르면 관측(mirror)을 baseline으로
쓴다. 교차 검증용이므로 남겨야 하는 기능이다. 스윕의 교정 호출은
`GuardSweepEnabled := false`로 차단 중이지만 mirror 갱신은 유지된다.

## 25-3. 오염 baseline — 확인됨, 정책 미정

1016에서 6초 대기(mirror 흡수) 후 사이클:

```
MINSTART → baseline captured 1016
MINEND   → geometry match 1016 → 교정 없음
```

볼 수 있는 모든 값이 1016이면 guardrail은 눈이 멀고, 영구 캐시 금지의
대가다. 선택지: (A) 감수 — 드리프트가 굳기 전 첫 복원에서 교정되는 게
정상 경로이므로, 오염은 guardrail이 꺼져 있던 사이 생긴 것만 남는다.
(B) zone을 fallback target으로 — §1.3(사용자 리사이즈 1150 보호)과
충돌하므로 불가. (A)로 가되 명시한다.

## 25-4. 재검증 시점 — 실측

교정 후 `+150/500/1000/2000/4000ms` 전부 974 유지. Chrome의 자체
재레이아웃이나 FancyZones 개입은 이 구간에서 없었다. 별도 버스트
재확인(0/120/300ms)은 불필요로 결론낸다.

## 25-5. 플랫폼 함정: 콜백 인자 상위 32비트

`idChild`가 0인데 `4294967296`(2^32)으로 도착했다. 32비트 LONG이 64비트
폭으로 넘어오며 상위가 스택 쓰레기다. 전 래퍼 진입부에서
`NormWinEventId`로 일괄 정규화한다. 부호 보존이 필요하므로
`(v << 32) >> 32`를 쓰고, `0/5/-8/0xFFFFFFFF/0x100000000` 5건 실측으로
확인했다. 최소화 경로만 고치면 나머지 핸들러의 필터가 조용히 어긋나므로
MoveEnd/Location/Show/Destroy 포함 전부 적용했다.

## 25-6. 절차: 스모크 테스트

Ahk2Exe가 미정의 함수 호출을 잡지 못하므로, 빌드 후 exe를 직접 기동해
프로세스 생존 + 시작 로그 + 로드 오류 0건을 확인한 뒤 설치한다. 이번에
이 절차가 `GuardEventWindowUsable` 정의를 통째로 지운 패치를 걸러내지
못한 것은, 스모크를 하기 전 빌드였기 때문이다. 이후 빌드는 전부 이
절차를 거쳤다.

## 25-7. 실사용 로깅 진행 중

하네스 없이 디버그 빌드를 설치하고 실사용을 로깅한다. 사용자가 창을
옮기거나 리사이즈하는 경우, 여러 앱, 스냅 창이 포함되어야 한다. "shell
disagrees" 빈도와 오염 케이스 출현율이 여기서 나온다. 결과가 깨끗하면
그때 스윕 교정 경로 제거를 결정한다.

# 26. 다섯 가지 확인점의 처리

## 26-1. 정규화 대상 구분 (signed LONG vs DWORD)

`event`/`dwEventThread`/`dwmsEventTime`은 시그니처에만 있고 본문에서
소비되지 않음을 grep으로 확인했다. 읽는 곳이 없으므로 부호 문제는
없다. `(v << 32) >> 32`는 `idObject`/`idChild`에만 적용되며, 5건 실측
(`0/5/-8/0xFFFFFFFF/0x100000000`)으로 산술 시프트·부호 보존을 확인했다.
`NormWinEventId` 하나로 전 래퍼(`MoveEnd/Location/Show/MinimizeStart/
MinimizeEnd/Destroy`) 진입부에서 일괄 정규화한다. `Destroy` 정리 누락
(슬롯·baseline 누수)도 함께 막힌다.

## 26-2. 스모크 테스트 판정 신호

릴리스는 `LogLine`이 침묵하므로 "시작 로그"는 신호가 될 수 없고,
로드 오류는 다이얼로그를 띄운 채 프로세스가 살아 있으므로 "생존"만으로
놓친다. 절차를 다음으로 고정한다: 빌드 → exe 직접 기동 → 8초 대기 →
(a) `#32770` 가시 다이얼로그 존재 여부 스캔 (b) 프로세스 생존
(c) 디버그 빌드면 시작 로그, 릴리스면 `wpm_debug.log` 부재 확인 →
종료 후 설치. `ahkrun run`은 (a)를 자동 판독한다.

## 26-3. 오염 baseline: 재시도 1회 (유보, §1.3 판단 포함)

오염 경로가 둘이다. WPM 시작 전부터 굳은 1016, 그리고 교정 실패로
굳은 1016. 두 번째만 막는다: 교정 실패 시 `{want, stuck}`을 세션
메모리에 1회분 남기고, 다음 캡처에서 셸·mirror 둘 다 `stuck`과 같을
때(=그 사이 사용자가 안 건드림)만 `want`로 재시도한다. 한 번 쓰고
버린다. 사용자가 중간에 리사이즈하면 둘 중 하나가 달라져 플래그가
취소된다.

§1.3 판단: 위반 아니다. `want`는 그 창이 올라와 있을 때 가졌던 실제
크기이며 zone 지식·DPI·상수를 쓰지 않는다. §1.4(1사이클 수명)는
1회성 연장이나, 단일 사용·자동 폐기로 한정되므로 정당화된다.
단, 의도치 않게 `stuck` 크기로 리사이즈한 경우 1회 오교정 후 로그가
남는다. (A) 잠정 채택, 실사용 출현율 후 확정.

## 26-4. 실사용 판정 기준 (먼저 수치로 고정)

사이클 요약 1행 형식:
`cycle hwnd=.. app=proc/cls arr=0/1 plc=WxH mirror=WxH actual=WxH decision=match|corrected|not-verified|gave-up`

- 분모: `decision`이 있는 restore 사이클, 앱(`proc|cls`)별 집계,
  `arr` 층화
- 통과: 앱별 최소 20사이클, 미교정 드리프트 0건, 교정 성공률
  (`corrected`/`mismatch`) 100%, `!!` 에러 0건
- `shell disagrees`율은 상한 없이 기록만 한다. 조건 빈도의 측정이지
  실패가 아니다
- `no-baseline` 복원은 분모에 넣지 않고 별도 집계한다

## 26-5. 릴리스 관측성

`LogAlways` → `wpm_guard.log` (128KB 로테이션). 에러 7곳, `giving up`,
`correction NOT verified`가 `LogBoth`로 양쪽에 기록된다. 디버그 전용
분기 부수효과 감사: `EventCount` 증가(로그 전용 카운터),
`Diag` 타이머 미설정, `LogLine` 조기 반환 — 동작 분기 없음. 릴리스
soak 6사이클: geometry 전부 유지, `wpm_guard.log` 부재(실패 0).

## 26-6. 측정 컨텍스트 주의 (DPI)

WPM 로그 좌표와 외부 도구 좌표가 정확히 2배 차이로 읽힌다
(WPM `7666|844|1948|1830` vs 외부 `3833|422|974|915`).
양쪽 모두 자기 공간에서 일관되며, 교정 루프(Set→재판독)가 같은
공간에서 닫히므로 기능상 무해함을 매트릭스로 확인했다. 보고서의
"물리 픽셀" 서술은 WPM 로그값에 대해서는 정정한다. 매니페스트
문자열은 바이너리에 있으나 효과 검증은 미결로 남긴다. 건드리지
않는다. 동작하는 루프를 DPI 추측으로 깨뜨릴 이유가 없다.
